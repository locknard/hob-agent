# hob-agent 交互设计评审 Decision Log

状态：已接受并进入 V2 交互基线
日期：2026-08-21
来源：`hob-agent-interaction-design-v1.pdf` 评审

本文把评审意见转为产品决策、交互语义与验收条件。标记为“已接受”的项目不在后续视觉
评审中重新讨论方向；后续评审只检查呈现是否准确、是否遗漏状态、是否能被实现和测试。

## DR-001：运行时放行与持久提案是两种对象

- **优先级：** P0
- **决定：** 已接受。
- **原因：** 运行时确认等待的是一次精确动作，必须在短 TTL 内放行；持久提案等待的是家庭
  对未来行为的判断，可以低压力地稍后处理。混在同一队列会同时破坏安全感与注意力模型。
- **交互：** Host Shell 提供两个稳定入口：
  - `等待你放行`：显示精确动作、影响、请求来源、允许确认的角色、剩余 TTL 与绝对过期时间；
    超时自动拒绝并写入审计。过期卡不可批准，只能重新发起并重新准备。
  - `给家的建议`：显示价值、证据、未知、冲突与自然过期时间；默认 14 天过期，过期可由新证据
    重新形成提案，不制造紧迫感。
- **TTL：** 由动作类型与 policy 决定，不使用一个通用时长。门锁等高影响动作示例为 30 秒，
  一般有人在场的可逆动作可以是 2 分钟；倒计时始终可见。
- **运行时拒绝：** “拒绝”只结束这一次动作，不写 `dedupKey` 闩锁，不影响未来重新准备同类动作。
- **过期留痕：** TTL 到期时写入一条家庭可读活动；用户下次打开产品时显示一次低调摘要，
  例如“昨晚 1 项放行已过期，未执行”。摘要确认后消失，审计永久保留。
- **验收：** 任何页面、badge、筛选、通知和活动记录都不得把两者合并为一个“待确认”数量。
  `runtime rejection -> dedup latch` 是不可发生组合。

## DR-002：收件箱三纪律必须成为可见承诺

- **优先级：** P0
- **决定：** 已接受。
- **Consent-first：** 批准建议方向不等于安装或启用；精确制品仍需第二次批准。
- **拒绝闩锁：** 用户选择“不再建议这件事”后，按 `dedupKey` 写入拒绝闩锁，并反馈：
  “好的，不再提议调整窗帘时间。”除非用户在决定历史中主动清除闩锁，否则相同对象永不再提。
- **积压上限：** 未决持久提案最多 5 个。满位时不生成第 6 个，也不以通知、提醒或换文案绕过；
  hob 显示“我先不再增加建议，等你处理这些”，记录被抑制的候选与反思原因。
- **Snooze：** “稍后提醒”改为显式时间选择，如“今晚 18:00 / 明天 / 下周 / 选择时间”。
  Snooze 保留对象并在约定时间重新露出，且**始终计入 5 个容量位**；“稍后”是延迟决定，
  不是腾出位置。拒绝则写闩锁，两者文案不得相似。
- **验收：** 重复提案、满位继续堆积、无期限 snooze 均为不允许状态。

## DR-002A：移动端也必须拆开两个时间语义

- **优先级：** P0
- **决定：** 已接受。
- **交互：** 移动端处理页固定把“等待你放行”放在上方，运行时卡显示独立倒计时 badge；
  “给家的建议”位于下方，显示自己的 `n / 5` 容量 badge。两类对象不能共享一个红点、数字或
  “待确认”聚合计数；底部导航入口不显示误导性的合并 badge。
- **验收：** 即使其中一个区块为空，另一类数量也不能被借用为总数；运行时区块只在存在有效
  或刚过期摘要时占据高优先位置。

## DR-003：确认动作必须经过成员权限与设备身份

- **优先级：** P0
- **决定：** 已接受。
- **角色基线：** Owner/Admin 可处理高影响确认；Adult Member 只能处理 policy 允许的范围；
  Minor/Guest 不得批准高影响动作。共享墙面屏在没有确认身份时只显示摘要与“发送到管理员设备”。
- **卡片：** 高影响动作明确显示“需要管理员”；不可执行的用户看到原因和可用的安全出口，而不是
  一个点击后才报错的按钮。
- **视图偏好：** 个人设备默认视图可以由本人修改；共享设备或家庭推荐默认视图需要管理员。
- **状态守卫：** `expired confirmation -> approve`、`unauthorized actor -> approve` 都必须无副作用失败。
- **验收：** 角色、设备、会话身份、TTL 和 snapshot revision 都是批准前守卫。

## DR-004：主动观察采用“明确推荐 + 显式同意”

- **优先级：** P0 / 产品战略
- **决定：** 已接受。
- **交互：** Onboarding 推荐“每周一次、安静时段、全部本地处理”的低频观察方案，但在用户明确
  点选“允许观察”前不创建调度。关闭仍是同级、无惩罚选择。
- **二次邀请：** 首次拒绝后至多在 7 天后由 hob 主动询问一次；不再周期性劝说。这个邀请本身
  也服从 consent-first，用户可选择“不要再问”。
- **衡量：** Phase 0 同时记录明确同意率、首份提案到达率、合并率和关闭率，不能只看通知打开率。
- **验收：** 默认值不等于暗中开启；推荐也不能省略用途、频率、本地处理和关闭后果。

## DR-005：解释入口与行为归因

- **优先级：** P1
- **决定：** 已接受。
- **交互：** 活动与异常卡提供“为什么”入口，展开自然语言 CauseRef 链，例如：
  “客厅灯 03:00 亮了 ← HA 自动化‘夜间感应’ ← 走廊传感器触发”。
- **归因：** 每条可归因活动显示 `手动/物理`、`hob`、`HA 外部规则` 或 `未知` 徽标。
- **物理覆盖：** 人工开关拥有最高即时优先级；与其冲突的自动动作被取消或抑制，并显示
  “你手动关了灯，我注意到了”。
- **验收：** 原始 bridge payload、私有推理和未脱敏工具参数不得进入解释层。

## DR-005A：纠正理解必须立即闭环

- **优先级：** P1
- **决定：** 已接受。
- **交互：** 用户纠正后，hob 必须显式回应“已更新”，并说明去向：事实或偏好写入家庭知识
  工作区；如果纠正要求改变未来行为，则只转成新的持久提案，不直接改变规则或设备。
- **验收：** `correction recorded + no visible acknowledgement` 与 `correction -> direct behavior change`
  都是不可发生组合。

## DR-006：一次性可逆动作提供短时撤销

- **优先级：** P1
- **决定：** 已接受。
- **交互：** 已验证成功后短暂显示“已关闭 · 撤销”，基线窗口 10 秒。撤销是一个新的反向动作，
  仍经过最新状态读取、policy 与审计；不可逆或状态已变化时不伪装可撤销。
- **验收：** 失败、结果未知或高影响不可逆动作不显示虚假的撤销。

## DR-007：安全级异常由 Host Shell 穿透所有布局

- **优先级：** P1
- **决定：** 已接受。
- **分级：** 安全级包含漏水、烟雾、燃气与 policy 判定的门锁风险；普通关注点包含舒适度、能耗
  和设备建议。两者不竞争同一个首页槽位。
- **交互：** 安全级异常置顶并穿透 Life、Control 和第三方布局；不能被 Provider 隐藏，也没有
  snooze。用户可以确认已看到，但告警只在危险解除或明确进入处置状态后消失。
- **验收：** Host Shell 的不可覆盖清单包含安全横幅、来源、新鲜度、主处置动作与求助出口。

## DR-008：Onboarding 是 hob “活过来”的仪式

- **优先级：** P1
- **决定：** 已接受。
- **交互：** 欢迎页由 hob 第一人称说明边界，并请家庭为它命名；名字写入 `SOUL.md` 第一行。
  家庭地图、观察偏好和第一问都由同一人格解释，但不假装成人类。
- **示例文案：** “我是 hob。开始时我只会看，不会动。你想怎么称呼我？”
- **验收：** 名字可稍后修改；跳过命名不阻塞；隐私和权限说明保持直接，不被人格文案弱化。

## DR-009：跨设备确认、批量治理与连接新鲜度

- **优先级：** P2
- **决定：** 已接受。
- **跨设备确认：** 语音发起高影响动作后，音箱说明确认被发送到哪些已认证管理员设备；
  第一个合格批准获胜，其他卡立即失效。没有合格设备时不执行。
- **批量动作：** 提交前预告分组，如“4 个直接执行，1 个需要确认”；安全子集可以先执行，
  需确认项形成独立运行时确认，结果逐项呈现，不以一个绿色总结果掩盖部分失败。
- **Freshness：** 同时表达连接健康、最后联系和最后有意义变化：
  - `连接正常 · 家中无变化`
  - `连接中断 · 最后联系 3 小时前`
- **验收：** 安静不得被误报为失联；失联不得被“更新于 3 小时前”含糊带过。

## V3 设计评审边界

V3 的评审会议把 DR-001 至 DR-004 及本轮补充视为“已接受、检查落图”，不再作为开放问题。会议只需决定：

1. 两类入口的视觉分量是否让用户既不焦虑也不忽略运行时 TTL。
2. 安全横幅在手机、桌面与墙面屏是否足够明显且不过度遮挡处置动作。
3. 角色与跨设备 handoff 的文案是否让非管理员清楚下一步。
4. CauseRef 链、归因与物理覆盖是否使用家庭语言，而不是技术日志。
5. Onboarding 的人格感是否增加亲近感，同时没有削弱隐私和能力边界。
