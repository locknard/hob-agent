## 二、目标模型

### 提案主线只有一次用户批准

```text
候选改进 → 准入（去重/闩锁/容量）→ 后台准备（证据·冲突·权限·编译·无写入模拟）
→ 准备完成才进收件箱 → 家庭一次决定 → 运行中的自动化（可暂停/关闭/恢复/回退）
```

- 无副作用的准备由系统提前完成，不消耗家庭批准。准备中的候选不占用收件箱，
  有独立、很小的后台资源上限。
- 用户看到的每一张建议卡都是完整方案：为什么、具体改变什么、与现有规则的关系、
  风险与权限、怎么暂停关闭恢复。
- 五个动作，各对应一句话后果：**启用**（自动化开始真实运行）· **修改**（形成新版本
  回准备）· **这次跳过**（结束本条，不写闩锁）· **不再建议**（写 dedupKey 闩锁并当面
  承诺）· **暂缓**（推到所选时间，占名额，最多两次）。
- 证据不足的三个出口：诚实回答未知 · 硬件/能力建议 · 只读观察计划（有结束条件、
  有预算、可随时停止）。不再用“试运行”占位。
- 启用后的安全来自：精确范围、权限、暂停/关闭/恢复入口、物理操作最高优先级、
  高影响动作逐次进入运行时确认。正常工作的自动化不打扰用户。

### 六类对象各走各的生命周期

| 对象 | 归属 | 是否进「给家的建议」 |
| --- | --- | --- |
| 回答/解释 | 对话 | 否 |
| 一次性动作 | 直接执行或运行时确认（TTL） | 否 |
| 安全告警 | Host 安全层，穿透一切布局 | 否 |
| 自动化建议（`automation-draft`） | 提案主线，一次启用决定 | 是 |
| 硬件/家庭洞察（`household-insight`） | 建议卡，无启用路径，只有“有帮助”反馈 | 是（动作文案独立） |
| 系统治理（`identity-link` / `capability-binding` / `action-authority-binding`） | 各自 Hub owner 的管理员入口 | 否，移出收件箱 |

### 3.2 重塑（产品行为）

1. **准备前置**：候选通过准入后自动完成证据、冲突、权限、Artifact 编译与无写入
   模拟；`ready` 才占收件箱名额；准备失败或证据不足的候选按业务稿合并、抑制或
   转为观察计划，不见用户。
2. **启用即真实生效**：启用 = 经治理部署路径把中立 Artifact 落成桥内（HA）可运行
   自动化 + 启用结果校验；失败是显式失败态，不是静默过渡态。
3. **启用后治理**：运行视图显示状态、最近一次结果、版本与创建者；提供暂停、
   关闭、恢复原配置；物理覆盖保持即时优先并成为后续调整证据；只有结果偏离预期
   时才再次打扰。
4. **修改闭环**：用户的修改意见形成新版本方案，回到准备，再以完整方案回来。
5. **观察计划**：目标、读取能力、结束条件、上限、结果、随时停止，全部明示；
   复用现有 observation scheduling 能力，不新造机制。
6. ✅ 已完成：`docs/v5-product-implementation.md`（原 v4）第 3、4 节已改写为
   一次决定与真实启用模型。

## 四、施工顺序（修订 DR-011）

1. **阶段一 · 一次决定，真的生效**：3.1 删除 + 3.2 重塑。提案治理收敛与真实
   启用/暂停/关闭/回退是同一个产品能力——分开做会产生“批准了但什么都没发生”
   的空转状态，这正是业务稿否定的东西。开工前先按业务稿“对 Proposal Store 的
   业务要求”重推技术稿。
2. **阶段二 · 数据能力**：世界模型补温湿度、在场、能耗投影与「当前关注」洞察，
   喂给首页、墙面屏、Web 总览。
3. **阶段三 · 界面组还原**：按 v5 修订后的目标分七组推进（日常高频 → 决定时刻 →
   对话 → 语音 → 安全 → 首次设置 → 墙面屏/Web），每组双视口对照验收。
4. **并行 · 设计 v5 修订**：3.3 需求单发回设计侧，阶段三开工前交付。

顺序调整的理由：界面组还原若先行，会忠实还原一个已被业务稿否定的提案模型，
返工必然发生；数据能力不依赖提案域，若有余力可与阶段一并行。

## 五、验收

- **不可发生组合**：`approved proposal → 第二次批准闸门`；`runtime rejection →
  dedup latch`；`correction → 直接行为变更`；任何 store/界面出现 trial 状态。
- **启用诚实性**：界面显示“运行中”当且仅当部署校验通过；失败显式可见并可重试。
- **注意力**：收件箱只出现 ready 方案；`pending + snoozed ≤ 5`；准备队列有独立上限。
- **成功指标**沿用业务稿：启用后是否很快被关闭或频繁人工覆盖，比批准率更重要。
- 每阶段完成定义：`pnpm test`、`pnpm check`、双视口浏览器验证、相关文档同步修订，
  全部有新鲜输出。
